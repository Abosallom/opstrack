## The 5 things Wave 3+ builders must know BEFORE they build

1. **`last_activity_at` is currently lying, and the digest/dashboard/follow-ups all read it.** A track move bumps the staleness clock (**C1**) because `entries_touch()` never subtracts `updated_by` from its diff. Three comments and `ADMIN.md:359-363` assert the opposite. Wave 3 builds meetings, the timeline, the dashboard and the digest on top of this column — **land the 0007 migration first**, or you will calibrate every staleness threshold against corrupted data and bake the bug into acceptance tests.

2. **`snapshot.health` is wrong, churning, and untested — do not treat it as authoritative.** It feeds the *priority-default* SLA to `computeHealth` instead of `resolveSlaDays()`'s track×priority answer (**S3a**), so the moment an admin uses 0006 every optimistic and offline row disagrees with the server and then flips on settle. Its Map identity is recreated on **every commit** after the first optimistic write (`derive()` returns the same reference only while `stale.length === 0`), so any `useMemo` you key on it re-runs constantly (**P2**'s real cost). And neither half of the reconciliation has a test (**S3b**). If you build meeting rollups or digest buckets off `health`, build them after S3.

3. **PostgREST silently clamps every read at 1000 rows.** Live-verified: `max_rows: 1000`. `MAX_ROWS = 2000` in `api/entries.ts:73` is unreachable, and `listHealth()` sends no limit at all (**C8**). Truncation arrives as a 200 with fewer rows — no error, no signal. Every new loader Wave 3 writes (meeting windows, timeline pages, digest ranges) must page or check `Content-Range`; "one working-set fetch" is not a safe assumption above 1000 open entries, and the app degrades into the client health mirror permanently when it happens.

4. **553 green tests are not evidence about the store.** Four load-bearing seams are mutation-survivable: `permissions.ts`'s narrow branch is unreachable from its own test (**S2** — this is the module the board's drag affordance reads), the realtime "one setState per 20-row batch" rule has no test at all (**S3c**), and both outbox drain concurrency invariants — the single-flush guard and the re-read-per-item rule — are unasserted (**S4**). `parse.test.ts` and `localeReach.test.ts` are genuinely strong; `store/**` is not. Do not read a green suite as a regression net for anything you touch in `src/store/`.

5. **The Arabic tree has zero bidi isolate characters, and every new mixed-direction string will ship broken.** I verified 0 occurrences of U+2066–U+2069 across all 23 `ar/` namespaces. Any string interpolating a user value (`«{title}»`) or showing a Latin token renders back-to-front (**S5a/S5b**) — and Wave 3 adds meeting titles, digest summaries and notification bodies, all of which interpolate. Adopt the convention *before* writing them: FSI…PDI (`\u2068…\u2069`) around interpolated values, LRI…PDI (`\u2066…\u2069`) around literal Latin tokens. There is no automated check for this today — `localeReach.test.ts` checks key/placeholder parity, not direction — so consider adding one in the same pass.

*Also, for Wave 4 specifically:* the top-ranked security item (**S1**) moves invite and throttle state out of `user_metadata` into a Postgres table with atomic CAS. Do not build the Members page against `meta.invite_hash` / `claim_fail_count`.
