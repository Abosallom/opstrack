Redeploy the Jira reader — done

Kept for reference, including the sign-in problem and how it was solved.

Confirmed live at 18:14 UTC on 21 August 2026

And a small surprise: it reports as version 1, created for the first time today. The other functions on the project are on versions 5 to 13. So this one had never actually been deployed before — meaning the version with the four security problems was never running anywhere, and the fixed one is the only one that has ever served a request. Better news than expected.

A small program runs on Supabase's computers and reads from Jira. Four security problems in it were found and fixed — but the fixed version is on your Mac and the old one is still the one running. These commands replace it.

1
Sign the command-line tool in. In Terminal:
npx supabase@latest login
It prints a code and opens your browser. Check the code on screen matches, click to approve, and come back to Terminal, which confirms the login finished.
2
Now the redeploy. Paste both lines and press Enter:
cd /Users/aziz/Claude/nphiescore npx supabase@latest functions deploy jira-read \ --project-ref lrysgpbkmuqgzsjesfkr --use-api
It prints progress for a while, then confirms the function was deployed and gives you back the prompt.

If you already tried and got “Access token not provided”

That is exactly this, and nothing was wrong with the command. The full message reads:
Access token not provided. Supply an access token by running `supabase login` or setting the SUPABASE_ACCESS_TOKEN environment variable.
It happens because the two Supabase access tokens were deliberately revoked during the security clean-up at the start of this project. There is nothing for the tool to sign in with until you make a new one — which is what step 1 does. Nothing is broken.

Nothing here can go wrong — and do it even if you never use Jira

No settings or passwords change; the program reads those fresh each time it runs. Running the command twice is harmless, and a failure leaves the old version running exactly as it was. You do not need Docker — that is what --use-api on the end is for.

The program is running either way; it was deployed months ago. Whether or not you ever point it at Jira, the version with the holes is the one sitting there now.

5

Prove the domain is yours

Optional. Two minutes. Nothing waits on it and nothing breaks if you skip it.

What this is for, in one sentence: it stops anyone else ever pointing nphiescore.com at their GitHub account and putting up something that looks like your tracker.

1
Go to github.com/settings/pages — type that address in directly. You want the section headed Verified domains.

This is the one place people go wrong

It is your account's settings, not the repository's. The repository has its own page also called “Pages”, with no Verified domains section on it at all — which is why it can look as though the instructions are wrong.

Yes: github.com/settings/pages   No: github.com/Abosallom/opstrack/settings/pages
2
Click Add a domain, type nphiescore.com, click Add domain. GitHub shows you a box containing two things to copy — a name and a long random value. Leave that page open.
3
At Hostinger, on the same DNS records page you used before, add one more record — this time choosing TXT as the type:
TXT
_github-pages-challenge-abosallom
3600
paste the long random value GitHub just showed you
4
Wait about two minutes, then click Verify on the GitHub page you left open. The domain moves into the verified list. Leave the record in place forever.

If Verify says it cannot find the record

Almost always impatience — the record has not spread yet. Wait five minutes and press it again. To watch for it, in Terminal — once this prints the value back, Verify will work:
dig +short _github-pages-challenge-abosallom.nphiescore.com TXT

6

Switch on the padlock

One tick box — but only after GitHub is ready, and it will not tell you.
GitHub makes a security certificate for your domain automatically. It just takes a while.

On GitHub, in Settings → Pages, there is a tick box called Enforce HTTPS. It is what puts the padlock in the address bar and stops anyone reaching the site without one.

Good news — the waiting is already over

Checked on 21 August 2026: GitHub reports the certificate for nphiescore.com as approved. So you can tick Enforce HTTPS straight away; the caution below no longer applies to you, and is kept only in case the domain is ever re-pointed.

The rule that made it worth waiting

If the tick box is greyed out, or the page still says it is provisioning, leave it alone. Ticking it before the certificate exists does not make the site less secure — it makes the site unreachable, for everyone, until the certificate arrives. Check back the next day.

How you will know it is ready

The provisioning message disappears and the tick box becomes clickable. Tick it, then visit https://nphiescore.com and look for the padlock next to the address. That is the last piece of the move.

Create the accounts

Part two. Stay at the keyboard for this one — it prints something you cannot get back.
They claim it at the sign-in screen, using the “First time here?” link.
1
Get a temporary key. Sign in at https://nphiescore.com/ in Chrome — it must be that address, because browsers keep this per web address. Then press ⌥⌘I to open the developer tools, click the Console tab, paste this line and press Enter:
const k = 'sb-lrysgpbkmuqgzsjesfkr-auth-token' JSON.parse(localStorage.getItem(k)).access_token
A long string in quotes. Copy it, without the quotes. It is not your password, it expires in about an hour, and that is plenty.
2
Run it for real. In Terminal, paste these four lines, putting your key between the quotes:
cd /Users/aziz/Claude/nphiescore set -a; . ./.env.local; . ./.env; set +a export ADMIN_ACCESS_TOKEN='paste-your-key-here' node scripts/provision-people.mjs --apply

If you see usage: apply [-a magic]

The command arrived split in two: --apply became -- on one line and apply on the next, and macOS has its own unrelated apply command that then complained. Nothing ran. Check the last line reads --apply with no break in it before pressing Enter, and run it again.

The sixteen codes print once and exist nowhere else afterwards

Not in a file, not in the database, not recoverable by anyone. Copy them out of the Terminal window before you close it. Lose one and that account must be scrapped and redone. Hand each person theirs directly. Never paste a code — or the key from step 1 — into a chat. If one ever does end up somewhere it should not, sign out of the app: that ends the session it belongs to.
