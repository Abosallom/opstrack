# Run 0031 — the PMO portfolio

**Two minutes. One file, pasted into the Supabase SQL editor, run twice.**

`supabase/migrations/0031_pmo_portfolio.sql` creates the tables the PMO section
needs: projects, initiatives, actions, risks, revenue, OKRs and milestones. It
is additive — it touches no existing table, no existing policy and no existing
function.

## Why it needs you

There is no way to run raw SQL from this machine. The `service_role` key reaches
PostgREST, which executes queries against tables that already exist; it cannot
create one. Migrations 0026–0028 went the same way, through the SQL editor.

## What to do

1. Open your project in Supabase → **SQL Editor** → **New query**
2. Paste the whole of `supabase/migrations/0031_pmo_portfolio.sql`
3. Press **Run**

**You should see:** `Success. No rows returned`, and in the Messages/Notices
panel:

```
NphiesCore 0031: 6 probes passed. 8 tables, 1 view, Jira reference on every table.
```

4. **Run it a second time.** It must succeed again and print the same notice.
   Everything in the file is `if not exists` / `create or replace` / `drop … if
   exists`, so a second run is a no-op. If the second run fails, the first one
   left something half-applied and I need to know.

## What it refuses to do

The file will not apply against a project missing `has_perm()`, `is_member()`
or `log_config_audit()`. It stops with a sentence naming which migration to run
first, before writing anything.

## What the probes check

They are not decoration — each one asserts a decision the file argued for, so a
project where one is untrue fails here rather than on a screen weeks later:

1. Eight tables and the objective-progress view exist
2. **No table stored a `variance` or `progress` column** — both are derived, and
   a stored copy disagrees with its inputs the first time somebody PATCHes one
3. **All eight tables carry `external_ref`** — your "referenceable from Jira
   everywhere" requirement, checked rather than assumed
4. Row level security is enabled on every one of them
5. A key result with `target = start` is refused (it would divide by zero)
6. Two revenue rows for one quarter are refused (they would double-count
   silently, and both rows look correct on their own)
