## 2. The apply

Supabase Dashboard → your project → **SQL Editor** → **New query** → open
`supabase/migrations/<file>` → copy **the whole file** → paste → **Run**. Read the NOTICEs. Then
paste and Run **the same file again**, in the same sitting, and read them again.

**The second run is the test, not ceremony.** Every `create table` skips, every `add column`
skips, every constraint, policy and trigger is dropped and recreated identically, every function
is replaced with itself, and the seed's `on conflict … do nothing` inserts nothing — and all the
probes still pass. If run 2 differs from run 1 in anything other than counts of rows that already
existed, stop and say so.

a stage, and "or beyond" is measured against the ladder). `0028` is independent of both and could

### What a failure looks like

```
ERROR:  NphiesCore 0026 FAILED: <a sentence saying exactly what is wrong and why it matters>
```

* Every refusal carries the `NphiesCore 00xx` prefix. They are apply-time messages for you and
  never reach the app.
* **A failure rolls the WHOLE file back.** There is no explicit transaction, so what Supabase runs
  is the file; if any probe raises, nothing landed. Fix and re-run.
* `CANNOT APPLY:` — a prerequisite file has not been applied here. The sentence names it.
* `CANNOT VERIFY:` / `FAILED: there is no unarchived track` — the workspace has nothing to hang a
  probe fixture on. Create or unarchive one track and re-run.
* `OT026` / `OT027` are the probes' internal rollback sentinels. You should never see one; if you
  do, it is a bug in the probe, not in your workspace.

## 3. ⚠ 0026 twice, back to back, BEFORE you rename anything

The seed's conflict target is `lower(btrim(name))`. Rename the seven rungs to the real programme
vocabulary and *then* re-run `0026`, and none of your new names collides — so the seed inserts the
seven English originals **again**. You get a 14-rung ladder, seven of them orphans nobody picked,
in every stage picker and every portfolio roll-up.

So: **both runs of 0026 first, in one sitting. Rename afterwards. Never re-run 0026 after a
rename.** If it happens anyway it is not silent — probe 1 prints the rung count and tells you to
delete the duplicates — but it is not prevented either.

**What is yours to do afterwards, all in the app (Settings › Catalogue, the third section):**

1. The real words for all seven rungs, English **and Arabic**. Arabic ships blank on purpose —
   those seven words are the programme's own vocabulary and a guessed translation is
   indistinguishable from a reviewed one on screen. The screen marks the untranslated ones.
2. `terminal` and `paused` where they belong. Shipped on **Live** and **Paused** respectively.
   `terminal` is what the portfolio's live count counts — never the word "Live", so renaming that
   rung is safe.
3. `expected_days`, the stalled threshold, on the rungs that should have one. It ships **unset
   everywhere**, deliberately: a threshold nobody chose is a number the app would start chasing
   people with. Setting it does **not** stop 0026 re-applying.

   **This is the step that turns the Stalled lens on, and until you take it nothing appears
   there.** `at risk` is *days on this rung past this rung's expected days* and nothing else, so
   with `expected_days` null everywhere the lens is empty for every organization in the
   workspace — correctly, and it says so with the *no threshold set* banner rather than with an
   empty list. Concretely, for the demo data: `docs/templates/structure.slice.csv` piles **18 of
   its 72 organizations on `Integrating`** precisely so that rung is the one worth a threshold.
   Give `Integrating` an expected days of, say, 14, and that pile becomes the stalled list as the
   clock runs. It will not be stalled on import day whatever you set — `stage_changed_at` is
   written only by 0026's own stamp trigger and the importer never sends it, so every imported
   organization reads **zero days in stage** the moment it lands.

## 5. Verify each file landed (paste and read)

These are the `PENDING-MIGRATIONS.md` "Verify live by" column made runnable, and they are the
column's contract: each goes false if the file is ever reverted.

**0026** — expect `7, 1, 1, 1, 1, map_node_progress_stage_stamp_trg,map_node_progress_touch_trg, p_ids, 0`

```sql
select
  (select count(*) from public.map_node_stages)                                     as stages,
  (select count(*) from public.map_node_stages where terminal)                      as terminal,
  (select count(*) from public.map_node_stages where paused)                        as paused,
  -- PARTIAL on purpose: name_ar is seeded blank on all seven, and a non-partial
  -- unique index would reject the second untranslated rung naming the wrong field.
  (select count(*) from pg_index i join pg_class c on c.oid = i.indexrelid
    where c.relname = 'map_node_stages_name_ar_uidx' and i.indpred is not null)     as ar_index_partial,
  (select count(*) from pg_constraint
    where conname = 'map_node_progress_pkey'
      and conrelid = 'public.map_node_progress'::regclass)                          as progress_pk,
  -- Postgres fires BEFORE ROW triggers in NAME order, so this string is the proof
  -- that the stamp runs before the touch. Invert it and a re-save of the stage a
  -- node already holds rewrites updated_by with nobody having edited anything.
  (select string_agg(tgname, ',' order by tgname) from pg_trigger
    where tgrelid = 'public.map_node_progress'::regclass and not tgisinternal)      as progress_triggers,
  -- PostgREST resolves the function from the body's KEYS. A drifted name is a 404
  -- the first time somebody drags a rung.
  (select proargnames[1] from pg_proc p join pg_namespace n on n.oid = p.pronamespace
    where n.nspname = 'public' and p.proname = 'reorder_map_node_stages')           as rpc_arg,
  (select count(*) from public.map_node_progress)                                   as progress_rows;
```

`progress_rows` is 0 until somebody records a stage — that is the no-backfill decision, not a
missing step. `stages` is 7 only until you add a rung of your own; `terminal` should stay 1 unless
you deliberately mean two rungs to count as arrived.

**0027** — expect `1, 1, 1, 0`

```sql
select
  (select count(*) from information_schema.tables
    where table_schema = 'public' and table_name = 'map_node_goals')                as goals_table,
  (select count(*) from pg_class c join pg_namespace n on n.oid = c.relnamespace
    where n.nspname = 'public' and c.relname = 'v_map_node_open_counts'
      and c.relkind = 'v')                                                          as view_present,

  -- version; anything falsy or absent means the view reads as its OWNER and

  (select count(*) from pg_class c join pg_namespace n on n.oid = c.relnamespace

```

## 6. After all three are live

### 6.1 The canary must not have moved

Run the verification query at the bottom of [`PENDING-MIGRATIONS.md`](PENDING-MIGRATIONS.md)
**unchanged** and confirm **`f_0025 = true`, `w_0025 = 1`, `x_0025 = 0`**, with every other column
exactly what it was before today.

None of these three files contains a `create or replace` or a `drop` targeting anything `0023`,
`0024` or `0025` created. Their tables are new, so their policies are new. **If the canary moved,
something else ran** — most likely an old file re-applied by hand. `f_0025 = false` means
`is_admin()` no longer calls `has_perm` and every custom role has quietly stopped being honoured;
`w_0025 = 0` means `map_nodes_insert` went back to `is_admin()` and the Director role silently
grants nothing on the tree. Both are repaired by re-applying `0025`, and only `0025`.

### 6.2 One stage change, one audit row — and none on progress

This is the pair of facts no probe inside the file could establish, because `now()` is the
transaction timestamp and does not move inside one statement.

**The ladder half, in the app** (Settings › Catalogue → the stage list). Note the current row
count first:

```sql
select count(*) from public.config_audit where table_name = 'map_node_stages';
```

1. Rename one rung and save. Re-run the count: **exactly one more row**, `action = 'update'`, with
   `before` and `after` showing the old and new name.
2. Open the same rung and save it again **without changing anything**. Re-run the count: **no new
   row**, and `updated_at` on the rung has not moved. That is the touch trigger's `else` arm and
   the audit trigger's `is distinct from` guard doing their job — a trail that fills with rows
   recording that nothing happened stops being read.

**The progress half, in the SQL Editor.** There is no screen that writes `map_node_progress` in
this wave — the stage picker arrives with the panel — so this one is checked by hand, and it
leaves nothing behind:

```sql
begin;
  select count(*) as audit_before from public.config_audit;

  insert into public.map_node_progress (node_id, stage_id, stage_changed_at)
  select n.id, s.id, timestamptz '2001-01-01'      -- a client value, deliberately absurd
    from public.map_nodes n
   cross join lateral (select id from public.map_node_stages order by sort_order limit 1) s
   order by n.id limit 1
  returning node_id, stage_id, stage_changed_at, updated_at, updated_by;
  -- stage_changed_at must come back as NOW, not 2001. The stamp OVERRULES a
  -- client value rather than rejecting it, which is why sending one reads as
  -- working and is not.

  select count(*) as audit_after from public.config_audit;
  -- Must equal audit_before. map_node_progress is deliberately NOT audited: this
  -- is day-to-day fieldwork, and a config trail dominated by routine data entry
  -- stops being read.
rollback;
```

### 6.3 The clock actually moves

Two writes in two separate runs, because one transaction cannot observe `now()` moving. Pick one
organization you do not mind touching, run the first block, wait a minute, run the second, then
run the cleanup.

```sql
-- run 1
insert into public.map_node_progress (node_id, stage_id)
select n.id, (select id from public.map_node_stages order by sort_order limit 1)
  from public.map_nodes n order by n.id limit 1
on conflict (node_id) do update set stage_id = excluded.stage_id
returning node_id, stage_id, stage_changed_at, updated_at;

-- run 2, a MINUTE later, and to a DIFFERENT rung
update public.map_node_progress
   set stage_id = (select id from public.map_node_stages order by sort_order offset 1 limit 1)
 where node_id = (select node_id from public.map_node_progress order by node_id limit 1)
returning node_id, stage_id, stage_changed_at, updated_at;
-- stage_changed_at MUST have moved, and updated_at with it.

-- run 3, the same statement again — a genuine no-op
update public.map_node_progress
   set stage_id = stage_id
 where node_id = (select node_id from public.map_node_progress order by node_id limit 1)
returning node_id, stage_changed_at, updated_at;
-- NOTHING may move. This is the arm that makes "the trigger is the only writer"
-- literally true, and it is the path a save-on-blur screen takes twenty times an hour.

-- cleanup: put that organization back to "nobody has said anything yet"
delete from public.map_node_progress
 where node_id = (select node_id from public.map_node_progress order by node_id limit 1);
```

Deleting the row — not setting `stage_id` to null — is what returns a node to "nobody has said".
`stage_id null` on a surviving row means somebody looked and cleared it, and the two are different
answers the whole feature rests on.

## 7. What the app already does, on both sides of the apply

The client half shipped **before** the SQL, on purpose: every name below is matched by string, and
a mismatch discovered *after* the tables exist is a precise sentence silently demoted to "Something
went wrong", with nothing failing to say so.

**Before you run 0026, today:** the app boots clean. Both new reads answer "no such table", the
config store keeps its previous (empty) rows and writes a console warning and nothing else — no
toast, no error screen, no retry loop (`src/store/config.ts:1015`). Settings › Catalogue shows its
third section reading **"No stages configured yet"** with a hint naming this migration
(`src/pages/settings/CatalogueAdmin.tsx:391`). That is the same empty state an applied-but-empty
ladder would show, which is why there is no flag, no version check and no second code path.

**The moment 0026 applies:** the next config load — a focus refetch inside 30 seconds, or a
reload — picks both tables up. Nothing latches, so no restart is needed.

**What is matched by name, and must never be renamed on one side alone:**

* Indexes / constraints → sentences, in `src/lib/pgError.ts`:
  `map_node_stages_name_uidx`, `map_node_stages_name_ar_uidx`, `map_node_progress_pkey`,
  `map_node_progress_node_id_fkey`, `map_node_progress_stage_id_fkey`,
  `map_node_stages_expected_days_chk`, `map_node_stages_name_len_chk`,
  `map_node_stages_name_ar_len_chk`, `map_node_progress_stage_chk`, and the 0027 set
